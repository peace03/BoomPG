# 문서 규칙 (Documentation Rules)

> 이 문서는 BoomPG의 **모든 문서를 지배하는 상위 규칙**입니다.
> 다른 문서와 충돌하면 이 문서가 우선합니다.

## 1. 왜 이 규칙이 존재하는가

BoomPG는 사람 1명 + AI 에이전트 여러 명(Claude=기획, Codex=구현, VARCO 3D=에셋)이
함께 만드는 프로젝트입니다. AI는 세션이 끝나면 기억을 잃습니다.
**문서에 적히지 않은 결정은 존재하지 않는 결정입니다.**

따라서 이 프로젝트의 진실 공급원(Single Source of Truth)은 대화가 아니라 `docs/` 입니다.

## 2. 문서 지도

모든 문서의 진입점은 [docs/INDEX.md](../INDEX.md) 하나입니다.
새 문서를 만들면 반드시 INDEX에 등록합니다. 등록되지 않은 문서는 없는 문서로 취급합니다.

```
docs/
  INDEX.md              모든 문서의 목차 + 결정 대기 목록
  rules/                지켜야 할 규칙 (이 폴더)
    documentation.md    문서 규칙 — 이 문서
    workflow.md         Claude / Codex / 사람의 역할과 작업 흐름
    code-style.md       C# · Unity 코드 컨벤션, 폴더 구조
  design/               게임이 무엇인가
    gdd.md              게임 디자인 문서
    glossary.md         용어 사전 (한국어 ↔ 코드 식별자 대응)
  tech/                 게임을 어떻게 만드는가
    architecture.md     시스템 구조
    networking.md       온라인 멀티플레이 설계
  pipeline/
    asset-pipeline.md   3D 모델 · 오디오 · VFX 반입 절차
  decisions/            왜 그렇게 정했는가 (ADR)
    ADR-template.md
    ADR-0001-*.md ...
```

계획서(`TaskPlan/`)는 문서가 아니라 **작업 지시서**입니다. 성격이 달라 `docs/` 밖에 둡니다.

## 3. 갱신 규칙 — 새로운 것이 생기면 그 자리에서 문서에 넣는다

Claude(아키텍트)는 아래 상황이 발생하면 **같은 턴 안에서** 해당 문서를 갱신합니다.
"나중에 정리하겠다"는 금지입니다. 나중은 오지 않습니다.

| 새로 생긴 것 | 들어갈 문서 | 추가로 할 일 |
|---|---|---|
| 게임 규칙·수치·승리 조건·캐릭터/무기 사양 | `design/gdd.md` | — |
| 새 용어 (한국어 기획 용어 ↔ 코드 식별자) | `design/glossary.md` | — |
| 새 시스템·클래스 군·씬 구성·데이터 흐름 | `tech/architecture.md` | — |
| 네트워크 권한·동기화·보정 방식 | `tech/networking.md` | — |
| 코드 컨벤션·폴더 규칙·네이밍 | `rules/code-style.md` | — |
| 에셋 반입 절차·명명 규칙·임포트 설정 | `pipeline/asset-pipeline.md` | — |
| 작업 흐름·에이전트 역할 변경 | `rules/workflow.md` | 필요 시 `CLAUDE.md`, `AGENTS.md` 동기화 |
| **되돌리기 어려운 선택** (엔진 기능, 네트워크 솔루션, 플랫폼, 장르 축) | `decisions/ADR-####-*.md` 신규 | 해당 주제 문서에서 ADR 링크 |
| 새 문서 파일 자체 | — | `docs/INDEX.md` 목차에 등록 |
| 완료된 계획서 | — | `TaskPlan/`에 날짜 붙여 보관 + INDEX 이력에 한 줄 |

### 3.1 갱신 절차 (항상 이 순서)

1. 대상 문서의 본문을 고친다.
2. 그 문서 맨 아래 **변경 이력** 표에 한 줄 추가한다.
3. 새 문서를 만들었거나 미결정이 늘거나 줄었으면 `docs/INDEX.md`를 고친다.
4. 사용자에게 "어느 문서의 무엇을 바꿨는지" 한 줄로 보고한다.

### 3.2 무엇을 적지 않는가

- 코드를 읽으면 바로 알 수 있는 것 (클래스 목록, 메서드 시그니처 나열)
- git 이력이 이미 기록하는 것 (누가 언제 무엇을 고쳤는지)
- 특정 세션에서만 의미 있는 임시 메모

문서는 **왜 그렇게 되어 있는지**와 **합의된 약속**을 적는 곳입니다.

## 4. 미결정 표기 규칙

설계 중 정해지지 않은 것은 반드시 눈에 보이게 남깁니다. 조용히 추측으로 메우지 않습니다.

문서 본문에는 아래 형식 그대로 씁니다.

```markdown
> **[미결정 D-###]** 로켓 발사 쿨다운을 고정값으로 둘지, 무기별로 둘지.
> 영향: `design/gdd.md` 전투 밸런스, `tech/architecture.md` 무기 데이터 구조.
```

(위는 형식 예시입니다. `D-###` 자리에는 실제 번호가 들어갑니다)

그리고 같은 항목을 `docs/INDEX.md`의 **결정 대기 목록**에 등록합니다.
ID는 `D-###`, 부여된 번호는 재사용하지 않습니다.

결정이 내려지면:

1. 본문의 `[미결정 D-###]` 블록을 **결정 내용으로 교체**한다. (블록을 남겨두지 않는다)
2. INDEX의 결정 대기 목록에서 해당 줄을 지운다.
3. 되돌리기 어려운 선택이었다면 ADR을 하나 쓴다.

## 5. 질문 규칙 — 애매하면 반드시 묻는다

기획·설계 과정에서 **해석이 둘 이상 가능하고, 어느 쪽을 고르냐에 따라 결과물이 달라지는 지점**은
Claude가 임의로 정하지 않고 사용자에게 질문합니다. 답변을 받은 뒤에 진행합니다.

- 질문할 때는 선택지와 **각 선택지의 대가(비용·난이도·나중에 바꿀 때의 파장)**를 같이 제시합니다.
- 사용자의 답변은 그 자리에서 문서에 반영합니다. 답변만 받고 문서에 안 적는 것은 규칙 위반입니다.
- 반대로, 업계 표준이 확립되어 있거나 나중에 쉽게 바꿀 수 있는 것(예: 필드 네이밍 스타일)은
  묻지 말고 기본안을 정해 문서에 적고 "이렇게 정했다"고 알립니다. 질문은 아껴서 써야 힘이 있습니다.

## 6. 작성 형식

- 언어는 한국어. 코드 식별자·파일 경로·명령어·에러 메시지 원문은 원문 그대로.
- 파일 인코딩 UTF-8 (BOM 없음), 줄바꿈 LF.
- 문서 제목은 `# 제목` 하나만. 그 아래는 `##`부터.
- 수치는 단위를 붙인다. `쿨다운 0.8초`, `넉백 12 m/s`, `틱레이트 30 Hz`.
- 단정적으로 쓴다. "적절히", "필요하면", "가능하면"은 금지어다. 값과 조건을 특정한다.
- 모든 문서 끝에는 변경 이력 표를 둔다.
