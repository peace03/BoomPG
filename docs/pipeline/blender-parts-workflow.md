# 원화 기준 파츠 보정 워크플로우 — 메인 목차

> 사용자 원화를 목표로, VARCO AI 생성 GLB를 시작점으로 삼는다.
> **파일 흐름: `.glb` → Blender(`.blend`) → `.fbx` + 텍스처 → Unity.**
> 작업 순서: 원화 분석 → 반입 점검 → 메시 수정 → 리토폴로지 → 텍스처 수정 → 8방향 검수 → FBX 내보내기 → Unity 반입·검증 → 보고.
> 수정 묶음마다 8방향을 확인하고 미충족 요소를 보정한다. 이미지 생성이나 파일 저장만으로 완료 처리하지 않는다.

## 0. 파일이 지나가는 흐름

### 적용 대상과 읽는 기준

이 절차는 신체·헤어·의상뿐 아니라 고글·아머·제트팩·무기·기계 부품 등 **개별 3D 파츠와 장비**에 공통으로 적용한다.
`부위`는 신체 부위 또는 부품의 특정 영역, `조립`은 캐릭터 부착 또는 부품끼리의 결합을 뜻한다.
예시는 판정 방법을 설명하며, 예시에 등장하는 구조·기능을 모든 모델에 새로 추가하라는 지시가 아니다.

| 대상의 실제 사용 방식 | 예시 | 공통 외관 검사에 추가할 검사 |
|---|---|---|
| 형태가 고정된 파츠 | 제트팩 본체, 고글 프레임, 무기 외장 | 평면·곡면·두께·개구부, 부착 방향·피벗·인접 부품 간섭 |
| 휘어지는 파츠 | 신체, 의상, 끈, 호스 | 실제 사용할 굽힘에서 체적·면 흐름·웨이트·관통 |
| 분리된 부품이 움직이는 장비 | 힌지 덮개, 회전 노즐, 슬라이드 부품 | 합의한 이동·회전 범위, 축·피벗·틈·충돌 |
| 여러 방식이 섞인 모델 | 강체 본체와 유연한 호스가 있는 장비 | 부품별로 분류하고 연결부와 조립 상태를 함께 확인 |

모델 이름만으로 분류하지 않는다. 고정된 장식 호스에 변형 검사를 강제하거나, 장비라는 이유로 실제 움직이는 부품의 검사를 생략하지 않는다.
리그·표정·Humanoid 항목은 해당 대상에만 적용한다. 적용되지 않음과 필요한데 검사하지 못함을 구별한다.
아래 캐릭터 예산·본 구성·파일명은 **BoomPG 프로젝트 규격**이며, 다른 용도에 그대로 일반화하지 않는다.

| 구간 | 파일의 역할 | 수행할 작업 |
|---|---|---|
| VARCO AI → Blender | `.glb`는 생성 원본 | 원본을 보존하고 Blender로 가져와 메시·재질·텍스처 점검 |
| Blender 안에서 작업 | `.blend`는 편집 원본 | 메시 수정 → 리토폴로지 → 텍스처 수정, 수정 묶음마다 8방향 검수 |
| Blender → FBX | `.fbx`는 Unity에 전달할 모델 | 검수한 `.blend`에서 FBX를 내보내고, 최종 텍스처 이미지도 함께 준비 |
| FBX → Unity | FBX·텍스처로 게임 에셋 구성 | 모델 Import Settings, Unity 머티리얼 연결, 크기·방향·외관·해당 변형 검증 |

이 워크플로우의 Unity 반입 대상은 **FBX와 최종 텍스처 파일**이다. `.glb`는 원본 보관,
`.blend`는 보정·재내보내기의 기준 파일로 관리한다. 재수정은 해당 `.blend`에서 수행하고 FBX를 다시 내보낸다.
텍스처를 `.blend` 안에 패킹한 것만으로 Unity 전달 준비를 마쳤다고 판단하지 않는다.
원본 GLB → 사용한 Blender 수정본 → 내보낸 FBX·맵 → Unity 반입 경로를 같은 작업 기록으로 연결한다.

## 1. 실행 순서와 상세 문서

처음에는 이 문서를 읽고 현재 단계의 상세 문서를 연다. 단계 전환 시 다음 문서를 읽는다.
각 상세 문서에는 **쉬운 용어, 입력, 작업 순서, 수정 규칙, 합격 기준, 실패 시 복귀, 토큰 절약법, 조사 출처**가 있다.

| 순서 | 상세 워크플로우 | 다음 단계로 넘길 것 |
|---|---|---|
| 01 | [원화 분석](blender-parts/01-reference-analysis.md) | 16개 분석 요소, 관찰/추정/확정, 크기·두께·디테일별 판정표 |
| 02 | [반입 점검·폴더·원본 보존](blender-parts/02-intake.md) | 원본 해시·수정 전 Blender, 메시·UV·맵·리그 현황, 별도 작업본 |
| 03 | [메시 수정](blender-parts/03-mesh-editing.md) | 기존 메시를 우선한 형태 보정본, 수정 범위·국소 치수·8방향 결과 |
| 04 | [리토폴로지](blender-parts/04-retopology.md) | 전체 검사와 필요한 부위 정리, 변형/강체 기준 검사, 베이크 기준 표면 |
| 05 | [텍스처 수정](blender-parts/05-texturing.md) | UV·색·패턴·표면 결·재질 맵, 큰 그림자 분리, 실제 채널·경로 |
| 06 | [8방향 검수·반복 보정](blender-parts/06-review.md) | 모든 적용 원화 요소 판정, 최신 8방향의 실제 확인 증거 |
| 07 | [FBX 내보내기·Unity 반입·보고](blender-parts/07-export.md) | Blender 재열기·FBX 재반입·Unity 검증, 파일 전달 경로, 완료/미실시 범위 |

```text
01 원화 분석 → 02 원본 GLB를 Blender로 반입·작업본 저장
    ↓
03 메시 수정 → 04 리토폴로지 → 05 텍스처 수정
    └─ 각 수정 묶음 완료 → 06의 8방향 전체 확인
                              ├─ 미충족 → 원인 단계로 복귀·보정 → 새 8방향 확인 ↺
                              └─ 충족 → 다음 단계
    ↓
06 최종 8방향 + 원화 비교 + 필요한 확대·측정
    ↓
07 최종 .blend 저장 → FBX + 텍스처 준비 → FBX 재반입 검사
    ↓
Unity 반입·머티리얼 연결·검증 → 보고·종료
```

메시 수정은 **모양**, 리토폴로지는 **면 연결**, 텍스처 수정은 **표면의 색·결·재질**을 다룬다.
UV가 바뀌면 색을 옮겨야 하고, 면 연결이 바뀌면 웨이트도 확인해야 하므로 이 순서를 따른다.
각 단계의 검사는 필수지만 이미 양호한 부분을 다시 만드는 것은 필수가 아니다.

## 2. 사용자가 확정한 운영 원칙

| 항목 | 확정한 규칙 |
|---|---|
| 파일 흐름 | **`.glb` → Blender(`.blend`) → `.fbx` + 텍스처 → Unity** |
| 메시 수정 | **기존 메시 우선, 부분 재구성 허용. 전체 재구성은 이유·영향·대안을 설명하고 확인받기** |
| 리토폴로지 | **전체 검사 후 필요한 곳만 정리. 얼굴·관절은 면 흐름, 강체 장비는 형태·면 수 중심** |
| 검수 주기 | **작업 중 해당 부위 확인, 수정 묶음마다 8방향 전수 확인. 최종은 원화 비교·필요한 확대 포함** |
| 문서 구조 | **메인 목차 + 단계별 상세 문서 7개** |
| 텍스처 | 가는 머릿결 음영·미세 홈·직물 결은 유지. 큰 그림자·방향성 반사를 고유색에 고정하지 않음 |
| 질문 | **시간제한 없음. 무응답을 승인으로 보거나 추천안을 자동 선택하지 않음** |

확정이 필요한 질문은 쉬운 설명·실제 모델 예·선택지의 차이를 함께 제시한다.
답변에 의존하는 작업은 기다리고, 독립적인 자료 조사·검사는 계속할 수 있다.
이미 받은 답변을 다시 묻지 않는다. 질문 대기 중에는 미정 사항과 다음 행동을 남긴다.

전체 재구성, 원화 밖 컨셉·파츠 구성 변경, 핵심 치수·가려진 구조의 불확실성,
새 유료 작업·예산 변경 등은 이유를 설명하고 확인한다. 승인 범위 안의 통상 보정은 진행한다.
새 도구·버전·셰이더의 동작이 불확실하면 공식 자료와 실제 환경을 확인한다.

## 3. 공통 파일·프로젝트 기준

- 작업 파일은 **캐릭터 → 파츠 → 원본/수정본**으로 관리한다. 공용 장비는 공용 폴더를 사용한다.
  원본을 보존하고 수정본 폴더당 활성 Blender 파일 하나를 둔다. 상세 구조·시간 표기는 [02](blender-parts/02-intake.md)에 있다.
- 수정본에는 관련 텍스처·원화·기록·내보낸 파일과 `8방향확인/<날짜_시간>/`을 연결한다.
  이전 검수·실패 이력을 덮어쓰지 않는다.
- 현재 모델 구성은 **통합 슈트(스킨드) + 헤어·고글·장비(강체)**다.
  [ADR-0008](../decisions/ADR-0008-모듈러-캐릭터-구조.md)의 2026-09-17 통합 슈트 개정과 최신 규격을 적용한다.
- 예산·축·피벗·맵·Unity 파일명 규칙은 [07](blender-parts/07-export.md)에 모았다.
  기존 문서에 남은 바디+별도 의상 설명이나 이전 머티리얼 규칙을 새 결정으로 적용하지 않는다.
- **폴더 정리만 요청받았다면** 경로·파일 무결성을 검증한다. 모델을 임의로 보정하거나 과거 시각 검수를 새 결과로 바꾸지 않는다.

## 4. 완료 조건

**외관 보정과 기술 검증은 따로 판정하며, 둘 다 충족해야 보정 완료다.**
면 수·매니폴드·UV 겹침·경로·FBX 재반입 검사가 통과해도 함몰·울렁임·번진 무늬가 고쳐졌다는 뜻은 아니다.
끈 제거·크기 변경처럼 일부 요구를 처리한 것으로 나머지 외관 결함까지 해결됐다고 판단하지 않는다.

- [ ] 사용자 지적과 반입 때 발견한 시각 결함을 문제 ID로 등록하고, 각 ID의 같은 조건 전후 확대 증거로 해결 여부를 확인했다.
- [ ] 원화 분석표의 필수 요소가 충족됐고, 적용 항목에 미충족·미확인이 없다.
- [ ] 추정·해당 없음의 근거와 사용자 확정 내용을 기록했다. 어려운 항목을 임의로 제외하지 않았다.
- [ ] 최종 수정 상태의 8방향을 실제로 모두 확인했고 원화 비교·필요한 확대·측정을 마쳤다.
- [ ] 메시·UV·재질·텍스처 경로와 원본 보존을 확인했다.
- [ ] 최종 저장·재열기, 내보내기 대상의 규격·재반입 검사를 마쳤다.
- [ ] 전체 흐름 완료를 보고할 때는 FBX·텍스처의 Unity 반입과 실제 검증까지 마쳤다.
- [ ] 파츠 보정과 리깅·조립·Unity 검증 상태를 구별해 [07의 형식](blender-parts/07-export.md#완료-보고-형식)으로 보고한다.

요청 범위가 Blender 보정 또는 FBX 전달까지라면 그 단계의 완료로 보고하고 Unity 반입·검증은 후속 상태로 남긴다.
Unity를 확인하지 않은 상태를 전체 흐름 완료로 표시하지 않는다.
미충족이면 원인 단계로 돌아간다. 정해진 반복 횟수만 채우고 완료하지 않는다.
도구 오류나 사용자 결정이 필요해 진행할 수 없다면 중간본과 남은 문제를 보존하고 미완료로 보고한다.
어렵거나 개선이 작다는 이유로 잔여 결함을 기록만 하고 종료하지 않는다. 승인 범위에서 가능한 보정을 계속한다.
Unity 연결 실패는 Unity 검증의 장애이며, Blender에서 가능한 메시·텍스처 보정을 멈출 이유가 아니다.
사용자가 결함 유지를 명시적으로 수용한 경우만 예외로 기록하며, 해당 결함을 `충족`으로 바꾸지 않는다.

## 5. 토큰 절약과 작업 이어가기

1. **필요할 때 읽는다.** 메인 + 현재 단계 + 필요한 정본만 읽고, 관계없는 문서·과거 대화를 반복 로드하지 않는다.
2. **원본 데이터는 로컬에 둔다.** 정점·픽셀·긴 로그 전체 대신 측정 요약, 실패 ID, 결과 경로를 반환한다.
3. **독립 검사를 묶는다.** 메타데이터·누락·면수 같은 검사는 도구에서 일괄 계산한다. 승인·편집·후속 검사는 순서를 지킨다.
4. **변경 영향만 재작업한다.** 입력·설정이 같은 검증과 정상 UV·맵은 재사용한다. 필수 8방향 확인을 줄여 절약하지 않는다.
5. **작업 기록 하나를 갱신한다.** 수정본 `Notes/`에 아래 상태를 남겨 중단·재개 시 필요한 부분만 읽는다.

```text
입력 파일·해시 / 현재 수정본 / 현재 단계 / 사용자 확정 사항
원화 문제 ID별 상태 / 마지막 변경 / 최신 8방향·검증 경로
시각 결함 ID별 원인·수정 전후 증거·잔여 문제 / 외관 판정과 기술 판정
답변 대기 질문(있을 때) / 다음 행동 / 완료·미실시 검증
```

토큰 절약은 반복 전송·불필요한 재작업을 줄이는 방식이다. 품질 검사 생략이나 절감률 보장을 뜻하지 않는다.

## 6. 조사 근거를 읽는 법

확인일: **2026-09-18**. 각 상세 문서의 `조사 근거`에서 원문과 적용 항목을 확인한다.
Blender 매뉴얼·Blender Studio 공개 자료·Adobe PBR/색 관리·Unity 공식 문서를 조사했다.
도구 원리와 사용자 결정, 프로젝트 규격을 구분했고, 판정표·실패 복귀 절차는 이 작업에 맞게 종합했다.
매뉴얼 버전·언어가 다를 수 있으므로 실제 설치 버전의 메뉴와 옵션을 확인한다.

토큰 운용 참고: [Anthropic — Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) ·
[Code Execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp).
필요한 자료만 읽고 도구 결과를 요약하는 원리를 적용하며, 새 유료 도구나 별도 에이전트를 필수로 도입하지 않는다.
