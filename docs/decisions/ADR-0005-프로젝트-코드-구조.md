# ADR-0005: 프로젝트 코드 구조를 확정한다 (폴더 · 어셈블리 · 로깅 · 테스트 · 데이터)

- 상태: 채택
- 날짜: 2026-09-14
- 결정자: YunPyeongHwa

## 맥락

첫 구현 계획서를 쓰려면 코드가 **어디에 놓이고 어떻게 나뉘는지**가 먼저 정해져 있어야 한다.
Codex는 설계 판단을 하지 않으므로, 이것이 비어 있으면 계획서를 쓸 수 없다.

다섯 항목(D-001 · D-002 · D-003 · D-007 · D-008)은 서로 얽혀 있어 한 번에 결정한다.
특히 D-002와 D-007은 독립 결정이 아니다 — Unity Test Framework의 테스트 어셈블리는
asmdef 없는 기본 어셈블리(`Assembly-CSharp`)를 참조할 수 없으므로,
**테스트를 도입하려면 프로덕션 코드도 asmdef 안에 있어야 한다.**

## 결정

| ID | 항목 | 결정 |
|---|---|---|
| D-001 | 폴더 구조 | `Assets/_Project/` 신설. 템플릿의 `Scenes/`·`Settings/`를 그 아래로 이동, `TutorialInfo/`·`Readme.asset` 삭제 |
| D-002 | 어셈블리 | 도메인별 `.asmdef` 분리 (Core / Gameplay / Network / UI / Editor / Tests) |
| D-003 | 로깅 | `BoomPG.Core.Logging.GameLog` 래퍼 도입. `Debug.Log` 직접 호출 금지 |
| D-007 | 테스트 | **EditMode 테스트만** 도입. PlayMode 통합 테스트는 만들지 않는다 |
| D-008 | 데이터 | 밸런스 수치는 `ScriptableObject`. `Assets/_Project/Data/` |

상세 규격은 [rules/code-style.md](../rules/code-style.md) 2·6장과
[tech/architecture.md](../tech/architecture.md) 7·8장에 있다.

## 이유

### 폴더 — 지금이 가장 싸다

`Assets/` 바로 아래는 앞으로 Fusion 2, 에셋 스토어 반입물이 폴더를 만들 자리다.
내 파일과 외부 파일이 섞이기 전에 경계를 그어 둔다. 파일이 열몇 개인 지금 옮기는 비용이
가장 낮다. Unity는 경로가 아니라 `.meta`의 GUID로 참조를 추적하므로,
`.meta`를 동반해 옮기면 URP 에셋 참조와 빌드 씬 목록은 끊기지 않는다.

### 어셈블리 — 레이어 원칙을 문서상 약속에서 컴파일 에러로 바꾼다

[tech/architecture.md](../tech/architecture.md) 3장의 레이어 원칙
(`Gameplay`는 네트워크를 모른다)은 현재 **문서에만 적힌 약속**이다.
단일 어셈블리에서는 `ExplosionResolver` 안에서 Fusion 함수를 직접 불러도 컴파일이 통과한다.
구현이 급해지면 실제로 그렇게 된다.

이 원칙은 [ADR-0004](ADR-0004-photon-fusion-2.md)의 위험 완화 장치이고,
Fusion 2는 D-014(모드 B 인원 상한) 실측 결과에 따라 뒤집힐 수 있다.
지켜지지 않으면 네트워크 솔루션 교체가 곧 게임플레이 전면 재작성이 된다.
asmdef 참조 표에서 `BoomPG.Gameplay`가 Fusion을 참조하지 않게 두면 컴파일러가 이를 강제한다.

부수 효과로 재컴파일 범위도 줄어든다.

### 로깅 — 호스트/클라 구분이 넉백 디버깅의 전제

이 프로젝트의 최대 기술 리스크는 넉백 동기화다([ADR-0004](ADR-0004-photon-fusion-2.md)).
호스트 권위 구조에서 로그가 어느 쪽에서 찍혔는지 구분되지 않으면 원인 추적이 불가능하다.
래퍼는 역할 접두를 자동으로 붙인다.

`[Conditional]` 속성으로 릴리즈 빌드에서 호출이 사라지므로, 매 프레임 도는 경로에 로그를
남겨도 출시 성능에 영향이 없다. 로그를 지우러 다니지 않아도 된다.

### 테스트 — 구현 검증을 말이 아니라 명령 출력으로 바꾼다

이 프로젝트의 워크플로우는 Codex가 구현하고 아키텍트가 검증하는 구조다
([rules/workflow.md](../rules/workflow.md)). 테스트가 없으면 계획서의 "테스트 계획"이
실행할 명령 없는 수동 확인 항목이 되고, 검증은 Codex의 보고를 믿는 것에 그친다.

넉백 테이블은 입력이 같으면 출력이 같은 순수 계산이므로 엔진 없이 검증할 수 있다.
D-022(다중 폭발 합성 규칙)의 결론도 테스트로 고정하면 구현 중 흐려지지 않는다.

PlayMode 테스트를 배제한 것은 작성·유지 비용 대비 이득이 낮기 때문이다.
게임의 재미는 어차피 테스트로 판정할 수 없다.

### 데이터 — 넉백이 적절한지는 플레이하며 만져봐야 안다

기획서가 모든 수치를 "프로토타입 시작값이며 플레이테스트로 조정 전제"라고 명시했다.
`ScriptableObject`는 **플레이 중 인스펙터에서 값을 바꿔가며** 즉시 체감할 수 있어
밸런스 반복 속도가 가장 빠르다. 재컴파일도 필요 없다.

JSON/CSV의 주된 근거인 "diff로 수치 변경 이력 추적"은 Unity `.asset`이 텍스트 YAML로
저장되므로 대부분 상쇄된다. 파서를 직접 만들 필요도 없다.

## 결과

- **열리는 것**: 첫 구현 계획서(M1 그레이박스)를 쓸 수 있다. 넉백 규칙을 자동 검증할 수 있다.
- **닫히는 것**: `Debug.Log` 직접 호출, 코드 `const`에 밸런스 수치 박기, PlayMode 통합 테스트.
- **초기 비용**: asmdef 6개 설정과 참조 등록, `GameLog` 구현, 템플릿 폴더 이동 작업.
  전부 첫 계획서(Step 1~2)에서 한 번에 처리한다.
- **영향받는 문서**: `rules/code-style.md`, `tech/architecture.md`, `pipeline/asset-pipeline.md`
- **되돌리는 비용**:
  - 폴더·asmdef — 높음. 코드가 쌓인 뒤 바꾸면 전 파일 경로와 참조가 바뀐다.
  - 로깅·데이터 — 중간. 호출부·참조부를 전부 고쳐야 한다.
  - 테스트 — 낮음. 나중에 PlayMode를 추가하는 것은 언제든 가능하다.

## 주의

asmdef 참조 표를 어기는 코드는 **컴파일 에러로 막힌다.** Codex가 구현 중
"참조가 안 된다"는 이유로 asmdef 참조 목록에 항목을 추가하려 한다면,
그것은 레이어 원칙을 어기려는 신호다. 임의로 추가하지 말고 아키텍트에게 보고해야 한다.
이 내용은 첫 구현 계획서의 "범위 밖"에 명시한다.
